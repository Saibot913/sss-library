### 1. Staff pages — Add Book, Edit Book, Returns/Holds, Dashboard

**Priority: low-medium.** Design settled 2026-09-14 through conversation; nothing built yet except the backend for Returns/Holds/Dashboard stats (see below — that part already works, just has no UI).

**IMPORTANT — staff schema correction:** `is_staff()` and the `staff` table are keyed by **`email`**, not `user_id`. An earlier draft of this doc (and the original `0002_staff_role_and_returns.sql` migration) assumed `user_id` — that was live schema drift, reconciled in `0013_reconcile_staff_email_schema.sql`. Any new staff-gated code should call `is_staff()` as-is (it already does the right thing) and not re-derive membership from `user_id`.

All four pages sit behind a hidden nav item / section, gated on `is_staff()`, invisible to regular signed-in patrons — same pattern as `return_book()`/`staff_return_book()`.

**1a. Add a Book — two paths, not one form:**
- **"Add another copy"** (the common case): staff searches/picks an existing book by title from the catalog, enters only a `location` for the new physical copy. Inserts one row into `copies` (same `book_code`, new `full_label`). No new `books` row.
- **"Add a brand new book"**: full form — `title`, `author`, `year_published`, `published_by`, `category`, `tags`, `summary`, staff-typed `book_code`, first copy's `location`. Inserts one row into `books` + one into `copies`.
- The form should detect an existing title as staff types and steer them toward path 1a before letting them create a duplicate `books` row for something that's really just a second copy. Don't auto-merge on a fuzzy match (the catalog already deliberately keeps 3 near-duplicate spellings of "Books by N Kasturi" as separate real records — see `CHANGELOG.md`) — only *suggest*, never force.
- **`full_label` for a new copy — corrected 2026-09-14 after checking real data:** the live convention is `book_code` alone for a single copy (e.g. `BO01`), or `book_code.NN` (zero-padded 2-digit suffix) for multiple (e.g. `DHV01.01` .. `DHV01.08`). It is **not** strictly sequential — `BV02` only has `.03` and `.05`, no gaps filled in — so these look like they were assigned by whoever physically catalogued the books, not generated by any program. Auto-suggest the next label (max existing numeric suffix + 1, zero-padded; `.02` if the only existing copy has no suffix at all) and pre-fill it, but leave it editable — same "suggest, don't force" pattern as `book_code`.
- `book_code` uniqueness: check live against existing values as staff types; if taken, auto-suggest alternatives (append `-2`, `-3`, ...).

**Architecture decision (2026-09-14): use `security definer` RPC functions, not raw RLS insert/update policies.**
Every existing sensitive write in this codebase (`checkout_book`, `reserve_copy`, `return_book`/`staff_return_book`) goes through a `security definer` Postgres function that checks a permission and does the write atomically — none of `books`/`copies`/`checkouts` has a raw client-facing `insert`/`update` RLS policy anywhere today (see `planning_docs/first-findings.md` §3). Adding a raw `insert`/`update` RLS policy on `books`/`copies` for this feature, as originally sketched, would be the *first* departure from that pattern in the whole project, and it's more invasive: it opens `books`/`copies` to direct client writes (shaped only by whatever the policy's `USING`/`WITH CHECK` clause manages to express), instead of a narrow function that does exactly one thing. The least-invasive move is to follow the existing convention:
- `add_book(...)` — checks `is_staff()`, inserts into `books` + first `copies` row atomically (one or the other alone would leave a book with no copies, or a copy pointing at nothing).
- `add_copy(p_book_code, p_full_label, p_location)` — checks `is_staff()` and that `book_code` exists, inserts one `copies` row.
- `update_book(p_book_code, ...)` — checks `is_staff()`, updates every column except `title`.
- `update_copy(p_full_label, p_location, p_status)` — checks `is_staff()`; see edge case below on `status`.

This needs a new migration (RPC functions + `grant execute ... to authenticated`), but **no RLS policy changes** — `books`/`copies` keep their existing public-read-only posture untouched.

**Edge cases for `update_copy`'s `status` field, decided 2026-09-14:**
- **Block changing `status` away from `checked_out` directly.** If a copy is currently checked out, staff must process it through the Returns page (§1c) first — that's what keeps `checkouts.returned_at` in sync. Letting Edit Book silently flip `checked_out` → `available`/`lost` would leave an open `checkouts` row forever, corrupting "active loans" and "days out" on the dashboard (§1d).
- **Clear any active hold when marking a copy `lost`/`damaged`/`withdrawn`.** If `reserved_by`/`reserved_until` is set (someone has it on hold) and staff retires the copy, null out both — otherwise the Holds table (§1c) keeps showing a hold on a copy that no longer circulates.

**1b. Edit an existing Book:**
- Editable at the book level: `title`, `author`, `year_published`, `published_by`, `category`, `tags`, `summary`. (`title` was originally locked — see git history / migration `0015` — but that turned out to be annoying in practice, so migration `0023` unlocked it.)
- Editable per copy (nested under the book): `location`, `status` (`available`/`checked_out`/`lost`/`damaged`/`withdrawn`).
- **Still needs:** an `update` RLS policy on `books`/`copies` restricted to staff — doesn't exist yet, needs a new migration (can likely be the same migration as 1a's `insert` policy).

**1c. Returns & Holds — backend already fully built, zero UI:**
- `staffReturnBook(fullLabel)` (`src/lib/checkouts.ts`) → RPC `staff_return_book` (`0009_staff_dashboard_rpcs.sql`). Marks a checkout returned, puts the copy back on the shelf.
- `fetchStaffCheckouts()` → returns every open checkout: book title, `full_label`, patron name, patron email, checked-out date, `daysOut`. **This is the return page's data source** — it's a table of what's currently out, with a "Mark Returned" button per row, not a single button or a typed input.
- `fetchStaffReservations()` / `staffForceReleaseReservation(fullLabel)` → same idea for active holds (a patron reserved a copy but hasn't picked it up yet) — a table with a "Release Hold" button per row. Free to include since it's already built.
- No new migration needed for this piece — purely a UI task wiring up existing, working functions.

**1d. Staff Dashboard — backend already built for the core stat, needs extending + UI:**
- `fetchStaffDashboardStats()` → RPC `staff_dashboard_stats` (`0010_staff_dashboard_stats.sql`) already returns: 30-day checkout traffic (day-by-day), total checkouts, active loan count, top 10 / bottom 10 books by checkout count.
- Additional metrics worth adding (new SQL, extend the RPC or add a second one) for a small honor-system community library — no fines/due dates, so keep everything informational, not punitive:
  - **Avg checkout length** (days between `checked_out_at` and `returned_at`, returned checkouts only)
  - **Category breakdown / trending categories** — checkouts grouped by `books.category`, so staff can see what genres/topics get read most
  - **Long-outstanding checkouts** — open loans out longer than some threshold (e.g. 30/60 days), as a gentle "might want to follow up" list, not a fine — pairs naturally with the open-checkouts table from 1c
  - **Active holds count** (from `fetchStaffReservations()`, already built) surfaced as a dashboard tile
  - **Total unique patrons who've ever checked something out** — community engagement, not just book stats
  - **New patrons over time** (from `profiles`, by creation date) if that timestamp exists
  - **Books never checked out** — separate from "bottom 10" (which still had *some* checkouts); a true zero-checkout list is useful for weeding decisions or for staff to give a highlighted book a push
- No fines, no overdue penalties, no due dates anywhere — this library is honor-system, confirmed.

### 4. Site access — 3 layers — DONE (2026-08-08)

**Status: executed and verified in a real browser** (screenshots taken, no console errors, unlock persists across reload).

Resolves the "public protected site (love all serve all) — 3 layers of vision" raw note. Confirmed with you this is a **permanent** "community only" wall, not a temporary pre-launch gate, and that a shared password is *not* meant to be real data security — just to keep casual outsiders/search engines out, since anyone who knows the phrase is treated as "one of us."

The 3 layers, as built:
1. **Site gate** — nothing renders until the shared password (`loveallserveall`) is entered. `src/lib/siteAccess.ts` holds the password + `localStorage` persistence (`hasSiteAccess()` / `grantSiteAccess()`); `SiteGate` in `App.tsx` is the full-page lock screen ("Sairam / Welcome to SSS-Library / Please enter password to access the site"), wired in as an early return at the top of the root `App` component.
2. **Guest view** — unchanged: public catalog browsing, same as before.
3. **Patron/staff view** — unchanged: real sign-in (`auth.ts`, email + one-time code) still separately unlocks holds and staff features on top.

Entering the password once is remembered per-browser (not per-visit) — confirmed as the simplest option, matching how the volunteer/review Google Form links were kept simple.

**Explicitly not a security boundary:** the code and `project-instructions/README.md` both call out that `books`/`copies` still have public `select` RLS policies, so this gate doesn't stop direct API access — only casual browser visits.

### 6. Bigger UI / readability — DONE (2026-08-08)

**Status: executed and verified in a real browser.** Went with the simplest option (site-wide bump, no toggle) per your call.

`html { zoom: 1.15; }` added to `src/index.css`. Went with `zoom` rather than a root `font-size` change — `App.tsx` is entirely hardcoded px inline styles, not rem-based, so a font-size cascade wouldn't have touched any of it. `zoom` scales the whole rendered layout uniformly, same mechanism as browser Cmd/Ctrl-+. Verified via a headless-browser check: `getComputedStyle(html).zoom` reports `1.15` and rendered element sizes scale accordingly, no console errors.

Browser support: Chrome/Edge/Safari, and Firefox 126+ (older Firefox would silently ignore it and render at normal size — not verified against an old Firefox, low risk given the audience is mostly mobile/modern-desktop, but worth knowing).

### 8. Staff hub restructure + per-book/library reviews — DONE (2026-09-16)

**Status: executed.** Two changes, decided together through conversation.

**Reviews, two kinds in one table:** `reviews` (migration `0019_book_reviews.sql`) — `book_code` is nullable: non-null is a review of that specific book (shown on its book detail page under "Reader Reviews"), null is a general library/site review (shown in the Community tab under "§ 04 What People Are Saying", a horizontally-scrollable list of the most recent 15 — explicitly *not* an auto-advancing carousel, decided in conversation so a visitor can read at their own pace).

- New RPCs `add_review`/`delete_review`, same security-definer pattern as everything else staff-gated — `reviews` itself is a public table (public `select`, no client insert/update/delete policy).
